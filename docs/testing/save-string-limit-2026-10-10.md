# 大档 Invalid string length 修复验证

日期：2026-10-10。状态：修复验证完成，已随 v3.6.2 发布正式站与测试站；不包含新 APK 或 GitHub 发布。发布回执见 [v3.6.2 验收](release-v3.6.2.md)。

## 问题与成因

玩家反馈第 393 回合保存当前个人档、生成近 100 回合续玩副本、保留旧档开新档均显示 `Invalid string length`。未取得玩家原始存档，本次使用同样回合数和真实时间线结构的独立测试数据复现。

完整存档先经过 `cleanSaveData` 的整档 `JSON.stringify`/`JSON.parse` 复制，校验阶段又将整档序列化为一个字符串。大档会在写入 IndexedDB 之前触发浏览器的单字符串长度限制。这三个操作均先保存完整原档，因此缩短续玩范围不能绕开错误。读取阶段也有解码后拼接完整字符串的问题。

同时，存档库为了列出节点信息调用 `getAllNodes()`，额外持有整份正文和状态快照，进一步增加了大档保存时的内存压力。完整备份失败会向上抛错，原有流程不会继续清空工作时间线。

## 修复范围

- 逐字段清理凭证并验证数据，去除整档字符串复制。
- 分块输出 JSON 和增量 SHA-256，校验字节与旧版 `JSON.stringify` 完全一致；不更改存档包版本。
- JSON/gzip 增量读取；仅对单个标量调用原生 `JSON.parse`，保留旧版 Unicode、转义和重复键行为。
- 保存格式、签名、危险字段、凭证和损坏 gzip 检查保持有效；调用方显式设置的读取容量限制继续生效。
- 列表改为 IndexedDB 游标逐条提取轻量节点信息，不在面板中常驻正文和状态快照。
- 联机转个人档的 sidecar 隔离检查使用精确 JSON 分块扫描，避免另一处整档序列化。
- 使用固定版本依赖生成可提交的浏览器 bundle，附带上游许可证；单文件打包和 public 同步包含新模块。

## 真实浏览器压力验证

运行 `npm run test:save-streaming` 中的 `scripts/save-library-string-limit-regression.mjs`，使用 Chromium、实际页面按钮、IndexedDB、gzip 文件和独立临时数据。没有玩家账号、真实存档或模型调用。

- 第 393 回合，590 个时间线节点，2 条分支。
- 完整 JSON 解码大小 **683,678,808 字节（652.01 MiB）**。
- 实测旧式整档 `JSON.stringify` 抛出 `Invalid string length`。
- 保存当前档后重新读取、签名校验通过，正文、日报、记忆和 IF 线完整。
- 近 100 回合续玩副本保留第 294–393 回合；393 条历史连续性记录仍在，完整原档及当前进度未被替换。
- 原档下载与已存 gzip 文件的 SHA-256 相同。
- 保留旧档开新档成功，刷新页面后可读回完整原档第 393 回合。
- 6 组通过；机器可读结果见 `reports/save-string-limit/result.json`。

这是合成大档验证，不代表已对该玩家未提供的原始文件验收。文件总量不再受单个 JavaScript 字符串限制；读取后的数据仍需要设备内存，单个极大字段仍受浏览器字符串限制。
