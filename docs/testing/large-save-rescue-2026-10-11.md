# 大档启动、原档救援与可选向量记忆

日期：2026-10-11。范围：本地实现与验证；未部署站点、未推送 GitHub、未发布 APK。版本仍为现有的 3.6.3。

## 已确认的问题与本轮修复

初始 1650 回合浏览器回归在启动到恢复正文的路径上记录到 4 次无上限 `timeline_nodes.getAll()`。完整快照、记忆和正文因此被多次物化；此前的流式 JSON 修复无法消除这部分读取。新实现把时间线目录与完整节点分开，日常启动/侧栏只读目录和所需节点；旧目录在 Worker 中逐条建立，升级数据库不重写原节点。冷压缩跳过无须处理的节点，运行时完整节点缓存最多 20 个，即使关闭自动归档也不会无限增长。

完整本地保存改为 Worker 逐条写入独立原档记录，不先组装整个 JSON 图。备份、校验记录数、切换工作档放在一个 IndexedDB 事务中；中途取消、空间不足、目录写入失败都会回滚。原始压缩节点保持原样，IF 线和损坏的原始节点也保留。重复保存未变化的同一档案复用原备份。

独立 `recovery.html` 不启动正文、Agent 或完整游戏 UI。首页启动失败入口及存档库可以进入救援页，支持：保留原档、直接导出、备份并开新档、按自定义回合数生成续玩副本（默认 100）、读取备份，以及从最近 30 个恢复点选择较早回合绕过损坏的最新回合。副本保留所选时点的角色、变量和已有历史记忆；完整旧正文和其他 IF 线留在原档中，不把未来状态复制到旧回合。历史分页及逐条生成副本的后续验证见 [可配置历史数量](history-window-2026-10-11.md)。

导出按节点清理、编码、计算校验和并压缩，保持现有 JSON/gzip 存档格式。直接导出当前档不需要先再占一份本地备份空间；如果导出期间当前档变化，则停止并说明原因，避免混合两个版本。云存档和灵希上传也使用这条流式导出通路。Service Worker 更新不再自动刷新正在运行的游戏，而是提醒保存后手动刷新。

## 向量记忆开关

设置中的记忆面板新增可选语义召回，默认关闭。关闭时不建向量数据库、不请求嵌入、不改变原有上下文组装。开启后配置兼容 embeddings 的地址、模型及独立本机密钥；每轮最多为 12 条新片段和本轮查询计算嵌入，复用未变化的缓存，最多召回 4 条，并受现有记忆提示预算约束。

只检索当前线路快照中已确认的历史及经纠正的记忆，不把未选择选项、计划、其他 IF 线未来当作事实。续玩副本可以检索自身保留的更早历史。向量缓存独立于游戏节点，最多 4000 条，不随每回合复制或写入导出包。清缓存不清记忆。检索有超时与离线回退；严格单次调用模式不发嵌入请求。本轮仅用模拟接口验证，没有调用付费模型。

## 实测证据

均为本机无头 Chromium、真实 IndexedDB 的合成档，不是玩家提供的 1650 层原档。时间为单次样本，硬件/负载会影响结果；`peakHeap` 仅为页面主线程 JS 堆采样，不是浏览器或 Worker 总内存峰值。

| 样本 | 启动与恢复正文 | 无上限完整节点读取 | 保留原档 + 导出 + 生成 10 回合副本 | 原档节点数 |
| --- | ---: | ---: | ---: | ---: |
| 1650 节点，已有目录 | 0.81 秒 | 0 | 5.29 秒 | 1650 |
| 3000 节点，真实 v1 旧库升级（每节点额外 8 万中文字符） | 3.45 秒 | 0 | 13.85 秒 | 3000 |

对应 `reports/large-save-rescue/1650-indexed.json` 和 `3000-legacy.json`。3000 节点最后一轮同时开启 CPU 采样；主线程堆采样约 47 MiB，后台救援阶段最大定时器延迟约 1.6 ms。启动仍有短时阻塞：该样本最大约 772 ms，另一轮曾约 2.23 秒，不能声称所有设备启动完全无卡顿。采样未发现启动时重新展开整个快照图，完整模块/界面初始化仍需后续优化。

## 边界与后续

本轮优先解决启动、保存、导出和救援。完整状态改为检查点/增量、跨节点正文与记忆去重尚未实施；旧版文件导入/合并及某些全图编辑仍可能需要较大内存。单个极大状态快照、手机实际内存压力也需要玩家原档和真机补验。

原档备份需要额外本地空间；空间不足时停止，不删除原档腾空间，可先直接导出。站点数据被浏览器清除或设备损坏不属于事务回滚保护范围，应保留导出文件。救援页需要在同一浏览器/同一站点访问，操作前关闭其他游戏页，避免另一个标签页继续修改当前档。
