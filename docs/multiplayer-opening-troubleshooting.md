# 联机开局不出正文排查

本次在 WSL 本地项目中使用 DeepSeek 官方 `deepseek-flash` 实测并修复（2026-09-27）。模型名称已通过官方 `/models` 接口核实，显示为 DeepSeek-V4.1-Flash；参见 [官方模型文档](https://api-docs.deepseek.com/quick_start/pricing/)。以下模型验证使用独立临时数据库和测试角色，没有修改现有玩家房间。首次修复随测试站构建 `2609271343` 部署；随后根据真实房间故障补上 MP-OPEN-05 和 MP-UI-01，已部署为构建 `2609271452`。服务端验证范围见[部署记录](staging-deployment-2026-09-27.md)。

## MP-OPEN-01：裁判通过审核后直接暂停，正文阶段没有启动

- 关键词：`INVALID_EFFECT_CONTRACT`、`world_state`、`scene_placement`、`set_presence_context`、`open_scene`。
- 实测原因：模型生成了服务器未注册的操作。语义审核批准后，正式冻结裁决时才执行 reducer 合同校验；错误没有返回裁判修复，导致正文模型根本没有被调用。
- 修复：裁判提示词提供从 reducer 注册表生成的合法操作列表；明确初始位置、时间等已存在于开局状态，没有真实变化时允许 `effects=[]`。冻结前执行与正式采用完全相同的编译校验，错误回到同一裁判会话，沿用有限修复次数；最终采用时仍会重新校验。
- 相关代码：`agent/prompts.js`、`agent/stage-orchestrator.js`、`persistence/sqlite-turn-workflow-repository.js`，均位于 `server/multiplayer/`。

## MP-OPEN-02：正文反复重写，最终 NARRATIVE_REPAIR_REQUIRED

- 关键词：`no visible canonical events`、`audiences`、`actor:import_...`、`RESOLUTION_AUDIENCE_COVERAGE_MISSING`。
- 实测原因：裁判把角色实体 ID 当作正文受众。投影器只按席位权限提供事件，因此正文模型拿到空事件列表；它不能修改裁决，又被要求引用有效事件，重写无法解决。
- 修复：提示词与输出合同明确使用 `seat:A` / `seat:B`。裁决采用前用真实投影器检查当前正文模式所需的事件覆盖；缺失时交还裁判，禁止把私密内容自动转成公开内容。`world_public` 仍只控制忍界公开投影，不能代替席位权限。
- 回归：SQLite 完整链路故意先返回错误受众，再返回未注册操作，随后修正。验证两个错误都在裁判阶段修复、审核和正文只执行一次、最终只产生一个裁决、一个正文与一个提交检查点。

## MP-OPEN-03：日报在符号、数字、字母之间反复修复

- 关键词：`shinobi_daily`、`flavor[].mark`、`格式无效`。
- 实测原因：联机给模型的 JSON Schema 仅说明“一个字符”，实际验收要求“一个汉字”。模型先后尝试符号、数字与字母，多轮失败后才生成汉字。部分输出还把 `source_refs` 错放到日报栏目内部。
- 修复：联机 JSON Schema 与首次、续修提示均从 `js/core/shinobi-daily.js` 的共享规则生成，覆盖汉字标记、字数、条数、任务等级顺序及固定字段；格式错误会给出具体期望。明确 `source_refs` 与 `daily` 同级。源文件已同步到 `public/js/core/`。
- 回归：同一份日报分别通过模型合同和实际交付校验，确认拒绝 `◇`、`1`、`A`，接受普通汉字与扩展区汉字；额外字段、栏目条数、任务等级顺序和短标题仍受约束。

## MP-OPEN-04：日报响应耗尽输出额度，finish_reason=length

- 关键词：`MODEL_OUTPUT_TRUNCATED`、`8000`、`thinking`。
- 实测原因：Flash 官方默认启用高强度思考；思考与最终 JSON 共用输出上限。连续性结算两次用尽 8000 token，分别没有可见 JSON 或只有截断 JSON。单独降低到 `reasoning_effort=low` 仍复现截断。
- 修复：仅对官方 `https://api.deepseek.com` 的 `deepseek-flash`，连续性结算请求使用 `thinking: {"type":"disabled"}`。此阶段只整理已经冻结的裁决、记忆和日报，服务器照常校验全部结果；裁判、正文及其他厂商的参数保持原策略。参考 [官方思考模式](https://api-docs.deepseek.com/guides/thinking_mode/) 和 [请求参数](https://api-docs.deepseek.com/api/create-chat-completion/)。

## MP-OPEN-05：正文已通过审核，记忆引用反复修正后暂停

- 关键词：`REPAIR_PAUSED`、`repair_turn_bundle`、`AUDIENCE_VIOLATION`、`subject_refs`、`event_refs`。
- 2026-09-27 测试站实际故障：裁决和正文审核均已成功，连续性结算却连续 8 次未通过。模型先把世界名、地名填入 `subject_refs`，再反复把新事件 ID 当成角色或任务实体 ID；最终仍有 2 项记忆未通过。旧界面同时显示“正在开局”和不醒目的绿色暂停提示。
- 根因：服务器验收使用受众分区的实体、事件白名单，提示词没有提供同一份完整白名单；错误反馈也未给出可用引用。模型无法从笼统的“超出绑定投影”判断该改用哪个 ID。
- 修复：模型与验收共用服务器生成的 `reference_bindings`，分别列出各记忆分区允许的事件、稳定实体和可改写条目；错误反馈提供有限数量的合法选择。每次请求都注入当前绑定，所以已经暂停的旧会话重试也能获得修正后的说明。私密引用检查继续生效，已通过的裁决、正文和结算项目继续复用。
- 恢复方式：本类故障可在原房间点击“重试未完成步骤”。这与 MP-OPEN-02 的已冻结错误裁决不同，无需重新开局，也不会提前发布尚未提交的正文。
- 回归证据：用实际错误形态构造 SQLite 完整链路，修复前重复 8 次后暂停；修复后一次纠正即完成提交。另有旧会话恢复、私密分区拒绝和合法引用提示测试。本次未自动恢复真实玩家房间，未新增付费模型调用。

## MP-UI-01：看不出是否正在生成，暂停提示与开局提示冲突

- 服务端在实际模型调用前发送阶段进度；成员读取接口提供当前阶段、开始时间、心跳、尝试次数与脱敏失败原因。刷新页面后可恢复进度，旧暂停记录也能从结算台账补出错误类别。
- 完整面板和悬浮窗共同显示“裁决／正文／审核／结算”四个阶段、已用时间，以及显眼的红色暂停卡。失败时说明是否已停止生成、保留了什么，并提供“重试未完成步骤”“刷新状态”“复制诊断”和详情。
- 断开实时连接或服务端心跳长时间没有更新时显示“状态待确认”，不继续假装正在生成。计时只刷新显示；每 10 秒的状态读取仅在生成期间发起，不会触发模型重试。
- 房间进入进行中后，旧的“正在开局”和“等待对方确认”提示退出显示；收起悬浮窗后，入口也显示“生成已暂停”。
- 浏览器回归覆盖完整面板、紧凑悬浮窗、手机宽度、失败重试、刷新、断线、诊断复制及计时不触发请求；服务端测试覆盖两个成员收到一致且不包含正文、凭据的阶段信息。

## MP-OPEN-06 / MP-PRESET-01：正文短、像规则说明，无法选玩家预设

- 根因：联机 Writer 使用独立固定提示词，没有读取浏览器的单人正文预设；提示大多是限制，裁判又容易把“没有替玩家行动”写成场景。审核曾把开局 NPC 的旧伤、过去丢失的信件误判为本回合新增变量，迫使裁判猜造未注册的 NPC 资源字段。
- 修复：房间可选择 A 或 B 的正文预设。每人同步自己浏览器当前主预设，服务器只向另一成员公开预设名称及摘要。首次锁定行动（开局由服务器锁定锚点）固定选择和内容；中途更换应用于下一回合。双方确认开局时自动同步本人预设；选择或修改当前采用的预设会清除旧开局确认。
- Writer 复用单人的 `resolvePresetMacros`、启用开关和条件条目；按联机独立变量阶段启用对应条目。文风、篇幅、视角、角色名及记忆宏进入正文请求。预设中的变量/日报标签不混入可见正文，联机仍由服务端原子提交状态、记忆和日报。
- 未配置预设时使用项目默认正文预设。开场建议 1200—1800 字；玩家预设的篇幅要求优先。质量检查会拦截明显的规则解释和防御性旁白，交回同一 Writer 修正。裁判为开场建立具体 NPC 事件与未决引子，审核区分初始背景和本回合真实状态变化。
- 官方 Flash 的联机阶段使用 `thinking=disabled`。实测正文、正文审核、普通行动裁判均曾用尽 8000 token 后截断；审核使用 `low` 仍有截断。改为把响应配额保留给完整结果，机械规则、状态合同和事实审核仍执行；厂商参数只发送给官方 Flash 端点，其他模型与兼容端点不受影响。
- 程序质量检查复用预设启用条件，识别“开场正文写 1500 至 1800 字”“正文至少 1500 字”等明确数字下限，按服务器计算的字数让作者补写；开局限定不误用于后续回合。建议篇幅和无法明确解析的自由表述保留为 Writer 提示，不猜测额外硬限制。事实审核不接管文风、氛围或润色偏好，不因“还不够丰富”等主观意见暂停回合。
- 操作：联机完整设置 → 正文预设 → 各自“同步我的正文预设” → “使用 A 的预设”或“使用 B 的预设”。已提交正文不会被切换预设重写。

## MP-OPEN-07：详细单人开局没有进入联机

- 原表单及后端只接受少量简化字段；角色资源、技能、装备使用通用初始值。
- 通过 `opening-draft-bridge.js` 复用单人 v3 草案、模板与 `character-creator`，并增加仅保存草案的模式。保存联机开局不初始化单人运行时，不写单人状态。
- 服务端使用同一 `buildOpeningState` 生成初始资源、技能、装备和私有羁绊，之后仍经过联机权限投影。创建时服务器读取完整双方草案；成员只能看到自己的身份秘密和关系秘密。B 保存时沿用 A 的共享起始时间。
- 入口：“详细开局 · 使用单人配置”。仅在新房间开局确认前编辑；既有回合状态不通过修改表单覆盖。

## MP-OPEN-08：日报引用修复每次只发现一个错误
